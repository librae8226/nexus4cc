# 对讲机模式 · 交互重设计（V2）

> 状态：**已实现**（2026-10-03，v4.10.0），在 Android 模拟器上逐条回归过。
> 与设计稿的差异见文末「实现后的修正」。
> 底层机制（本机 ASR、投递、回复追踪）沿用 v1，见 [`WALKIE.md`](WALKIE.md)。
> 本文只谈"手感"和"信息怎么摆"。

---

## 一句话

**下半屏是一个固定不动的物理旋钮，上半屏是这个旋钮对面那个人的工作现场。**

v1 把旋钮当"屏幕的主角"放在中间，还让它随内容伸缩。结果：它既不够像实物，又挤占了本该
用来看内容的地方。v2 把它按到下面去、钉死尺寸 —— 旋钮是**手**用的，不是**眼睛**看的。

## 1. 布局：旋钮钉在下半屏

```
┌────────────────────────────────────┐
│ 对讲机                    🔊  ↻  经典 │  44px  应用级操作
├────────────────────────────────────┤
│                                    │
│   ┌──────────────────────────┐     │
│   │ 你说 · 14:23             │     │  ← 内容区：可滚动
│   │ 把 README 更新一下        │     │     你的话 / 工作过程 / 摘要
│   └──────────────────────────┘     │
│   ┌──────────────────────────┐     │
│   │ ● 正在工作  12s           │     │
│   │   ⚙ Bash   sleep 7        │     │
│   │   📖 Read   README.md     │     │
│   │   ✎ Edit   README.md  ›   │     │
│   │   🤔 正在整理改动说明…      │     │
│   └──────────────────────────┘     │
│                                    │
├────────────────────────────────────┤
│  ~/work/nexus                      │  ← 读数面板：这一格是谁
│  ● 对讲机测试 · 空闲                 │
├────────────────────────────────────┤
│           ╭────────────╮           │
│        ╭──┤  按住说话   ├──╮        │  ← 旋钮：固定尺寸，不随内容变
│       ╱   ╰────────────╯   ╲       │
│      │                      │      │
│       ╲                    ╱       │
│        ╰──────────────────╯        │
└────────────────────────────────────┘
```

**尺寸**：`--dial: min(84vw, 330px)`，只跟屏幕宽度有关，**不跟内容有关**。旋钮占地一旦
确定就不再变，内容多少只影响上面那块滚动区。

**为什么放下面**：竖屏单手，拇指的自然落点就是屏幕下 1/3。v1 的旋钮在中间，拇指要往上够，
而且内容一多就把它压小 —— 一个会缩水的物理旋钮不成立。

**键盘**：点了 ⌨ 起输入法时，旋钮会被键盘盖住。这是可以接受的（打字时不需要旋钮），但
内容区必须跟着 `visualViewport` 收缩，保证输入框始终可见。

## 2. 圆心：一个圆，两种手势

你说的对 —— 圆心以前显示"CH 05"确实没意义。但**把"按住说话"和"发送"做成两个按钮塞进
圆心会互相挤**（可用的环宽只有 20 多 px，够不上一个像样的点击目标）。

所以按你原本那句话的字面来：**它就是同一个圆，用两种手势区分。**

| 手势 | 行为 | 什么时候有 |
|---|---|---|
| **按住** | 说话（松手结束 → 精炼） | 永远 |
| **轻点** | 发送 | 只在框里有草稿时 |

判定：按下时长 < 300ms **且**这一段没录到任何音频（轻点几乎必然如此）→ 算轻点。
麦克风还没打开过时不判定为轻点（避免首次按下被权限框拖长、误判成发送）。

**圆心上的字会跟着变**，这就是"教手势"的地方：

```
   没有草稿              录音中               有草稿
 ╭────────────╮      ╭────────────╮      ╭────────────╮
 │            │      │            │      │            │
 │      ●     │      │      ■     │      │      ➤     │
 │  按住说话   │      │  松手结束   │      │    发送     │
 │            │      │            │      │ 按住可重说   │
 ╰────────────╯      ╰────────────╯      ╰────────────╯
```

> **这一条是最值得你拍板的**。备选方案是"把发送做成圆心外的一个窄环"（几何上能塞下，
> 但环宽只有 ~24px，点击目标偏小），或者"发送挪到圆心正上方做成一条弧形键"（好点，但
> 就不是你说的"中间"了）。我倾向手势区分：零额外几何、拇指不用挪、且和微信语音消息
> 的心智是通的。

**误发怎么防**：轻点只在"有草稿"时有效，而草稿是刚刚精炼过、你正打算发的东西；再加上
发送时给一声明显不同的"咻"（音效，见 §4），发出去不可能没察觉。

## 3. 这一格是谁：工作区用路径，频道是个人

旋钮外圈 = **工作区**，读数直接显示文件夹路径（`~/work/nexus` 而不是 `main`）——
路径本身就是它的意思，不用再解释。

旋钮内圈 = **Agent**，显示 channel 名。

读数面板上再补一个**状态点**，旋钮于是同时是一块状态牌：

| 状态 | 含义 |
|---|---|
| `● 空闲` | 这个 Agent 停在那里等你说话 |
| `◐ 工作中 12s` | 正在干活，切过去就能看它的过程 |
| `○ 没在运行` | 这一格不是 Claude 会话（v1 的护栏，发过去会被 shell 当命令执行） |

**这样"切换频道"这件事才真的成立**：你不是在切一个代码窗口，你是在**换一个人讲话**，
而且换过去之前就知道他忙不忙。

## 4. 手感：两级反馈

你描述的"中间也要有更轻柔的咔嗒、到节点更重"，本质上是把每一格再细分：

```
一格（= 换一个 Agent）
  ├─ 细分 1  ···· 轻"嗒"（只有声音，无震动）
  ├─ 细分 2  ···· 轻"嗒"
  ├─ 细分 3  ···· 轻"嗒"
  └─ 节点    ─── 重"咔"（声音 + 震动）
```

| | 声音 | 震动 |
|---|---|---|
| **细分** | 又短又轻又尖（~12ms，带通 3.2kHz，音量 ~0.15） | 无 |
| **节点** | 现在的"咔"（~48ms，带通 1.8kHz，音量 ~0.5） | `Haptics.selectionChanged()` |
| **吸附到位** | 低沉的一声"咚" | `Haptics.impact(Medium)` |

**为什么细分不震动**：一秒钟能划过十几个细分，每个都震会让马达变成背景噪音、手指发麻，
反而把"到节点了"这个信息淹掉。**震动只留给节点，才让节点显得重。**
（"震的时候必须有声音"这条我们满足：节点同时出声 + 震。）

细分密度：每格 4 个细分。太少（2 个）听不出连续感，太多（8 个）会糊成一片。

**静音开关**：细分音会让声音变成持续背景，标题栏放一个 🔊 开关。

## 5. 他在干什么：一行行的动作流

这是 v2 最重要的一块 —— 你说的"文本不断跳动、刷新，显示他在工作的过程"。

**数据从哪来**：不是去解析终端画面（脆），而是读 Claude Code 自己写的 transcript。
每个工具调用在里面都是结构化的，还常常自带一句人话描述：

```json
{"type":"assistant","message":{"content":[
  {"type":"tool_use","name":"Bash",
   "input":{"command":"ls -la","description":"List repo root"}}]}}
```

**一行怎么提炼**：

| transcript 里 | 屏上显示 |
|---|---|
| `tool_use: Bash` | `⚙ Bash   <description，没有就截断 command>` |
| `tool_use: Read/Edit/Write` | `📖 Read   src/server.js`（只看文件名，可点开） |
| `tool_use: Grep/Glob` | `🔍 搜 "walkie"` |
| `tool_use: Task` | `👥 派了个子任务：<description>` |
| `thinking` block | `🤔 推理中…` |
| `text` block | 直接进"摘要"区（那是它说的话） |

**怎么刷**：沿用现有的 `/reply` 轮询（1.2s），把 `steps` 一起带回来，前端只 append 新行并
自动滚到底。不需要 WebSocket —— 一行一行冒出来的观感，1.2 秒的节奏已经够了。

**点得开**：凡是带文件路径的那一行，**点一下直接在文件浏览器里打开那个文件**（见 §6）。
这就是"看着他在改，改完点开看"。

## 6. 结果怎么看：页面给摘要，详情去文件

你的判断是对的：手机上塞不下工作结果，而且结果本来就是**文件**。

分工：

| | 显示什么 |
|---|---|
| **对讲机页** | 只有**摘要**（一两句 + 可播报）。够判断"成了没有、要不要细看" |
| **文件浏览器** | 详情。复用 Nexus 现成的 `WorkspaceBrowser`，**根目录就是当前这一格的 cwd** —— 换一格，看到的目录跟着换 |
| **过程里的文件名** | 可点，直接跳到那个文件 |

`WorkspaceBrowser` 已经支持 `initialPath` + `overlay`，可以直接嵌。要加的就一件事：
给它补一个命令式的 `openFile(path)`（现在只暴露了 `closeEditor`）。

> 这一块正好是你说的那个比喻：**能听见他说话（摘要/播报），也能看见他电脑上的东西（文件）。**
> 两件事在同一个屏幕上，但分属两个层次 —— 说话是"结论"，文件是"证据"。

## 7. 播报：修掉那个"联动"

你观察到的现象是个真 bug，不是错觉。两个按钮共用了同一个 `speakingNow` 状态：

```tsx
// 现在的代码
{speakingNow ? hush() : void play(summary, ...)}   // ▶ 摘要
{speakingNow ? hush() : void play(reply.text, ...)} // ▶ 全文
```

于是播摘要时**两个按钮都变成"⏹ 停止"**，点"全文"执行的是停止 —— 想从摘要切到全文，
必须先停一次。

改成记录**在播哪一个**：`speaking: 'summary' | 'full' | null`。按钮只在"自己正在播"时
显示停止；点另一个就是**直接切过去**（先掐断再播），不用先停。

顺带两条：
- **自动播摘要**保留（松手后听见一句结论，是对讲机的核心体验），但如果你正在看屏幕或
  已经手动点过播报，就别抢。
- 播报中的那一条要有可见的进行态（按钮呼吸 + 一行波形），否则不知道是在播还是卡住了。

## 8. 明确不做

- **不做流式 WebSocket**：1.2 秒轮询够用，少一套状态要维护。
- **不在对讲机页里渲染完整 markdown 回复**：那是文件浏览器和老终端的活。
- **不做多频道同时收听**：一次只有"当前这一格"。
- **不把旋钮做成可缩放/可拖拽**：它是个实物，位置尺寸固定。

## 8.5 回复里的文件引用可以直接点开（实现时加的）

原设计里"看文件"是个按钮，得自己再去目录里翻。既然 Claude 的回复本来就带路径
（`` `src/walkie/api.ts` ``、`[README](./README.md)`），那让它直接可点就没必要多这一步。

`frontend/src/walkie/replyLinks.tsx` 认三种写法，按可靠性排序：

| 写法 | 例子 | 处理 |
|---|---|---|
| markdown 链接 | `[README](docs/X.md)` | http(s) 走外链；其余当路径 |
| 反引号 | `` `src/walkie/api.ts` `` | 像路径就可点，否则按普通代码渲染 |
| 裸路径 | `docs/WALKIE.md` | 后缀在白名单里才认 |

**白名单是必须的**：没有它 `v4.9.1` 会被当成文件名（`.1` 也能匹配 `\.\w+`）。
路径后面的 `:12-15` 行号会被剥掉——文件浏览器还不能跳行，留着只会让路径打不开。

点下去不是只开浏览器，是**直接定位到那个文件所在的目录并打开它**。

## 9. 已知取舍

- **轻点发送 vs 按住说话**共用圆心，需要一次学习。用圆心上的字 + 两种不同的声音来教。
- **细分音**会变成持续的背景声，所以给了静音开关。
- **动作流只有"工具级"粒度**：看不到工具内部的输出（比如命令的回显）。想看那个就点文件名
  或去经典终端 —— 那里本来就是为此存在的。

## 10. 实现后的修正

三处在实现时定下来的、和设计稿不一样的地方：

**① 圆心不是两个按钮，是一个按钮的两种手势**（见 §2 的说明）。几何上塞不下第二个
像样的点击目标；手势区分零额外尺寸、拇指不用挪。判定是「按下 < 300ms 且这一段没录到
音频」——轻点本来就录不到东西，所以不会误伤"想说话但按太短"。

**② 认领会话改成靠位置，不靠文本。** 实现过程中在真机上抓到一个 bug：Claude 早就答完了，
界面上却一直停在"已投递"。原因是我们靠"transcript 里那条发言和你发的文本对得上"来认领
会话，而那条消息在终端里被多敲进了一个字符，前 24 字比对就失效了 —— 于是永远等下去，
正是 §7 说的那个老毛病换了个地方复发。

现在：发送前记下文件大小，之后**追加的第一条人类发言**就是我们发的那句。文本对得上只是
更强的确认，不是必要条件。另外补了一条 60 秒兜底：文件认了却始终找不到那句话，就明确
报「这条消息没有出现在会话记录里」，而不是让界面转到超时。

**③ 摘要之外，短回复整段摊开。** 设计稿说"页面只给摘要"，但回复短的时候（< 700 字）
折叠反而挡住了里面的文件引用。所以短的直接展开，长的才折。

## 10.5 第二版调整（v4.11.0）

真机用过一轮之后改的四处。

**内外圈对调：外圈 = Agent，内圈 = 工作区。** 外圈更大更好抓，而"换个人"是更常用的动作。
颜色跟着语义走（琥珀=工作区、内圈；蓝=Agent、外圈），CSS 变量也从按位置命名
（`--ring-outer`）改成按语义命名（`--ring-ws` / `--ring-agent`）——对调之后按位置命名
会读起来很绕。

**两个圈都能无限转下去。** 做法是把连续值当成无界的（可以到 7.3、-2.1），只在取索引时
取模；刻度角度用"绕回来的差"（`wrapDelta`）算，所以过界那一刻是接上的，不会跳。
间距也随之改成 `360/n`——循环之后这才是"铺满一圈"的自然间距。

**拨动时读数实时跟跳。** 以前只有松手才更新，于是得一个个拨过去看才知道转到哪了。
读数改成从**旋钮自己的连续值**算，不等父组件；父组件只在松手时被通知一次。
必须这么分：父组件的 `onChannelChange` 会打断语音、清空草稿、去拉上一轮回复，
每过一格调一次既不必要也很贵。

**草稿按频道各存一份，并落盘。** 打了一半被切走 / 锁屏 / WebView 被系统回收，字都还在。
键是 `project:channel`，存在 `localStorage` 的 `nexus_walkie_state` 里（防抖 400ms），
顺带记住"上次停在哪一格"，回来直接回到那一格。

**反馈强度**：三档震动全部改用 `impact`（Light / Medium / Heavy），
因为 `selectionChanged` 必须先 `selectionStart()` 才会震 —— 插件源码里是
`if (this.selectionStarted)`，所以早先"每过一格震一下"其实**一次都没震过**，
摸到的只有吸附那一下。声音也整体加强了，并且把细分音从 3.2kHz 挪到 2.2kHz：
手机小喇叭在高频衰减很快，原来那档推不出来就是"听不见"。
