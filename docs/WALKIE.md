### 第 8 轮 · v5.0.0：补全基础能力，把交互磨到位（2026-10-03）

这一轮没有新概念，四件事都是**现有东西缺的那一角**。判断标准还是那三条（第十节末）。

| # | 你提的 | 落地成什么 |
|---|---|---|
| 54 | **留一个常驻的文件浏览器入口**，能快速 navigate 到任何地方 | 输入框那一行的**最左一个键**（📁）。常驻的意义是"永远在同一个地方"—— 不用找。点开 = **你正对着的那个人**的目录，进去就是现有那个 Nexus 文件浏览器（面包屑 / 上级 / 隐藏文件 / 排序都在）。不做手输路径栏：你不会手输，进去了就能导航 |
| 55 | **每一条对话里也能去到这个人的工作区** | 署名那一行拆成**两个各自说自己意思的靶子**：点名字 = 回复给这个人，点路径 = 打开他的目录。两个都 ≥32px，都按"它写的是什么"分给谁 |
| 56 | **它在问问题给选项时，要能选** | 选项从 transcript 里结构化地读出来（label + description），**画在流里的那条消息下面**，点一下就是回答。后端把那一下翻译成终端认的方向键序列。输入框在提问期间**停用**并说明原因（见下） |

| 58 | （顺手补齐的两处） | **折叠屏展开时的阅读宽度**：一行拉太长、眼睛要来回扫，而这一屏的职责就是"扫一眼" —— 内容给 760px 居中，输入那一行跟着收窄。**服务器地址可改**：APK 里的地址是装机时带上的，地址一变手机上就没地方改了，只能清数据 |

**为什么输入框在提问期间必须停用**（这条是实测出来的，不是设计洁癖）：
终端里那道题还开着的时候，往输入框打的字会被它吞掉，而回车会替你按在**当前高亮的那一项**上。
也就是说，不拦的话你会得到一个"我没选它，它却收到了"的答案 —— 那比不让发糟得多。

**按键序列是试出来的**（真 pane 上一条条验）：
选项行在纯文本里是 `❯ 1. [ ] 面条`，**高亮项带 `❯` 前缀**，所以"光标现在在第几项"是读得出来的 ——
不必假设"面板刚弹出时它一定在第一项"。

| 面板形态 | 怎么答 |
|---|---|
| 单选单题 | 回车**直接选中并提交**，面板自己关掉（不用再按别的） |
| 多选 | 行首带 `[ ]` 复选框，回车是勾选；勾完切到 Submit 那页再回车 |
| 一次多题 | 几页标签（`← ☐ 午餐 ☐ 几点起 ✔ Submit →`）。**答完一题它自己翻到下一题** —— 这时候绝不能补一个 `→`，那会跳过一整道题；答完最后一题它自己停在 Submit 页，回车即提交 |

每一步之后都**重新读一次面板**再决定下一步。

**阅读面板的那几行也要认准。** 屏幕上别处也会有 `1. xxx`（模型自己写的编号列表就紧贴在面板上面），
把它们算进来，"面板还在不在"的判断就会误判。判据用面板自己的签名（最后那行键位提示），
再往上走**走到编号 1 就停** —— 选项从 1 开始编号。也不能拿分隔线当中止符：面板**下面**也有一条。

**用自己的话回答**：面板里那一项写着 `Type something.`，和 Esc 是一回事 —— 它是**跳过**这道题。
跳完之后你那句话就是一条普通消息发过去，它照样接着办（实测反馈是「记下了」）。
所以输入框在提问期间**照常能发**：点了发送先跳过、再把你说的话送出去。顺序不能反 ——
题还开着的时候，打进输入框的字会被它吞掉。

**两条防线**（答错比不答糟得多，所以宁可不发）：
- 题目原文一起送到后端，发按键前**核对屏幕上那道题是不是这一道**。防的是一个真会发生的竞态：
  你在电脑前顺手答了，手机上那条卡还没消失（流最多 5 秒才刷一次），这时点选项 ——
  面板早翻页了，盲按就会按在下一个能按的东西上。
- 收答案那页（`Review your answers / Ready to submit`）上**也印着题目**，光对题目会对上。
  所以先看有没有那一页 —— 那一页的回车是"提交现有答案"，不是"选这一项"。

**同步**（你问的：在经典界面/网页里增删了 project 或 channel，这边跟不跟）：
跟。流每 5 秒（有活在跑时 1.5 秒）重新拉一次清单，它本来就是从 tmux 实时读的，不存快照。
实测：`POST /api/sessions` 建的窗口下一个轮询就出现在选人面板里，`DELETE` 掉的当场消失；
选人面板每次打开都从"你现在对着的那个人"重新起头，不沿用上一次的高亮（那个工作区可能已经不在了）。

### 1. 版面：三个带

```
┌────────────────────────────────────┐
│ 对讲机                 🔊 ↻ 📁 ⌨ 经典│  状态条：应用级操作
├────────────────────────────────────┤
│                                    │
│   │ 他上一轮 · deepseek            │  屏：这一轮的通话记录，**从下往上长**
│   │ 完全明白了                      │
│   ┌──────────────────────────┐     │
│   │ ● 正在工作  12s           │     │
│   │   ❯ Bash   sleep 7        │     │
│   │   ◫ Read   README.md      │     │
│   │   ✎ Edit   README.md [打开]│     │
│   └──────────────────────────┘     │
├────────────────────────────────────┤
│      ~/work/nexus  ~  ~/work/server │  ← 台面：调台条（两行）
│   APK ●空闲  对讲机测试  apk stevejobs│
│  ┌──────────────────────────────┐  │
│  │        按住说话               │  │  ← 讲话键：占满整个拇指区
│  └──────────────────────────────┘  │
└────────────────────────────────────┘
```

**为什么内容贴底（`justify-content: flex-end`）**：通话记录是从讲话键往上长的。
内容少的时候它贴着台面站，那块空就读作"还没收到"；一旦居中，空就变成"这里本来该有东西"。

**尺寸固定**：台面只跟屏幕宽度有关，**不跟内容有关**。内容多少只影响上面那块滚动区。

**为什么不放中间、不随内容伸缩**：竖屏单手，拇指的自然落点就是屏幕下 1/3；放中间拇指要
往上够。而且会随内容缩水的按键不成立 —— 它是**手**用的，不是**眼睛**看的。

**键盘**：点 ⌨ 起输入法时台面会被盖住。可以接受（打字时不需要它），但内容区要跟着
`visualViewport` 收缩，保证输入框可见。

### 2. 台面：两排**可读**的条子 + 一个大键

上两版是**同心双圈**（外圈 Agent / 内圈工作区）。旋钮好用的前提是每个档位有你能看见的
位置和名字 —— 而那两个同心圈转起来是十几个**无名刻度**：你只能盲转、瞄一眼读数、再转。
那是在"找"，不是在"调"；而且内外圈的半径差只有几十像素，拇指要挑着落点。

**换成了两行横向条（`Tuner.tsx`）**：每一项都带名字，左右邻居都在视野里，你**知道**往哪边拨。
底子直接用浏览器原生的滚动吸附（`scroll-snap`），惯性、橡皮筋、跟手都是系统的，不是模拟的；
手感只负责"按格配音、按格震动"。

| 行 | 显示什么 |
|---|---|
| 上排 · 工作区 | **文件夹路径**（`~/work/nexus`）。路径本身就是它的意思，不用再解释 |
| 下排 · Agent | channel 名 + 状态。选中那一格才展开状态字，其余只有一个小灯 |

**状态**（于是台面同时是一块状态牌）：

| 状态 | 含义 |
|---|---|
| `空闲` | 停在那里等你说话 |
| `工作中` | 正在干活，切过去就能看它的过程（小灯在闪） |
| `就绪` | 还没跟他聊过，不知道忙不忙 |
| `不是 Claude` | 这一格不是 Claude，发过去会被 shell 当命令执行 |

**两排各配一色**（琥珀 = 工作区、蓝 = Agent），CSS 变量按**语义**命名（`--tone-ws` /
`--tone-agent`）而不是按位置。

**拖动时不惊动父组件。** 本组件自己跟"转到哪了"，只在**停稳**时提交一次。必须这么分：
父组件的换台处理会打断语音、清空草稿、去拉上一轮回复，每过一格调一次既不必要也很贵。

### 3. 讲话键：这一屏唯一的主角

它是整块屏里最大的东西，**整块都是命中区** —— 拇指不用瞄。有草稿时它**变成两个键**
（按住重说 / 发送），没有猜测。

**为什么不再是"一个圆两种手势"。** 上一版把"按住说话"和"轻点发送"塞进同一个圆心，
判定靠"按下不到 300ms 且这一段没录到音频"。为了不误伤，还得在按下瞬间把框里的字偷偷
存起来（因为"开始录音"会清空输入框）。一个圆扛两件事，代价是这一串补丁。
现在两件事各有各的键，**不需要猜**。

| 状态 | 键上写什么 |
|---|---|
| 待机 | `按住说话` / `松手自动精炼成一条指令` |
| 录音中 | 整块变红 + 你的电平画在键上 + `松手结束 · 2.4s` |
| 转写收尾 | `转写最后一段…`（不可按，是块仪表） |
| 它在干活 | `已投递 · 12s` / `正在输出 · 40s`（不可按） |
| 有草稿 | 左：`按住重说`　右：`发送`（蓝色大键） |
| 这一格不是 Claude | `这一格不是 Claude` / `发过去会被当命令执行 · 点这里换一个` |

最后一行是**键自己把话说清楚**：点它是"跳到下一个能用的 Agent"。
上一版是"上面一行黄字警告 + 下面一个照常能按的讲话键"—— 你会对着一个明知会被拦住的
东西按下去，白说一遍再被拒。

**误发怎么防**：发送是要有草稿才出现的独立键，而发送时另给一声明显不同的"咻" + 一次重震，
发出去不可能没察觉。

### 4. 台面的手感

**两级反馈。** 每一格再细分：

```
一格（= 换一个 Agent）
  ├─ 细分 ···· 轻"嗒"（只有声音，无震动）
  ├─ 细分 ···· 轻"嗒"
  ├─ 细分 ···· 轻"嗒"
  └─ 节点 ─── 重"咔"（声音 + 震动）
   停稳吸附 ── 低沉一声"咚"（震动更重）
```

| | 声音 | 震动 |
|---|---|---|
| **细分** | 短而轻（18ms，带通 ~2.2kHz，振幅 0.34） | 无 |
| **节点** | 重"咔"（55ms，带通 ~1.8kHz，振幅 0.78 + 一层 430Hz 的 body） | `impact(Medium)` |
| **停稳** | "咚" | `impact(Heavy)` |

三处都是踩出来的：

- **细分为什么放在 2.2kHz 而不是更高**：手机小喇叭在 3kHz 以上衰减很快，原先放在 3.2kHz
  且振幅只有 0.13，结果就是"听不到"。往下挪一个八度 + 提到 0.34 才真的听得见。
- **细分为什么不震**：一秒钟能划过十几个细分，每个都震会让马达变成背景噪音、手指发麻，
  反而把"到节点了"这个信息淹掉。**震动只留给节点，节点才显得重。**
- **震动别用 `selectionChanged`**：它必须先 `selectionStart()` 才震（插件源码里是
  `if (this.selectionStarted)`）—— 早先那版"每过一格震一下"其实一次都没震过。
  三档现在都用 `impact`。

细分密度 3 个/格：2 个听不出连续感，8 个会糊成一片。

**条子能一直拨下去。** 到底自动接上另一头（原生滚动吸附给的），所以不存在"拨到头了"。

**拨动时读数实时跟跳**：选中态从**条子自己的连续位置**算（"哪一项的中心最贴近容器中心"），
不等停稳。松手吸附时才对父组件提交一次。

**讲话键上的反馈**（这一整条链都在 `feedback.ts` 里）：

| 时机 | 声音 | 震动 |
|---|---|---|
| 按下讲话键 | `squelch()` —— 电台的静噪被打开，一记被硬切断的静电 + 低频闷响 | Light |
| 松手 | `roger()` —— 两个上扬短音，对讲机的"通话结束" | Medium |
| 精炼稿落进输入框 | `land()` —— 比 tick 更闷更轻的一声 | — |
| 发送出去 | `whoosh()` —— 带通 900→2600Hz 的上扬气流 | Heavy |
| 他答完了 | `roger()` —— **同一句"结束"**，于是"这轮完了"是听出来的，不用盯屏幕 | — |

**静音开关**：细分音会变成持续背景，所以标题栏留了一个 🔊。

### 5. 他在干什么：**他说的话**是标题，工具是它下面的证据

**数据从哪来**：不是去解析终端画面（脆），而是读 Claude Code 自己写的 transcript。

**v4.13.0 把这件事整个反了过来。** 老版本一行行显示的是**工具名**（`Read` / `Grep` /
`Edit` / `推理中…`）—— 那是**实现细节**，不是"他在干嘛"。用户的原话是：
「显示一个动作调用动作，然后显示"推理中"，完全不知道它在干嘛。」

而他其实已经把意图用大白话写下来了 —— transcript 里每条工具调用之间都夹着
一句人话（"先看一下现在的实现"、"找到问题了，是重复旋转"）。我们原来把它扔进
`replyParts`、只在最后才拿出来。**反了。**

现在一屏是**按"章"排的**：

```
│ 第 1 步：执行 `sleep 15`。          ← 他说的话（左竖线，正常字色）
│   ▸ Sleep 15 seconds               ← 支撑它的动作（暗一档、小一号）
│                                     ── 分隔 ──
● 正在运行 Sleep 15 seconds           ← 「此刻」：一条**状态**，不是一步
```

| transcript 里 | 屏上 |
|---|---|
| `text` block | **一章的标题**（他说的那句话）。也照常进 replyParts |
| `tool_use: Read/Edit/Write` | 章下面一行 `✎ walkie.css`（可点开）。**Edit/Write 加粗**——它在动你的仓库 |
| `tool_use: Bash/Grep/Glob/Task` | 章下面一行 |
| `thinking` block | **不进列表**。它是状态不是进展，只喂给底部那行「此刻」 |
| `tool_result` | 把对应那一步标成 done，于是「此刻」知道该撤下来了 |

**「此刻」为什么单独一行**：把它混进上面的列表，就成了"每想一次记一笔"的噪音 ——
一屏里会跳出十几个"推理中…"，而它们全都是同一件事。它现在在最底下，带一个呼吸的点，
说的也是人话（"正在读 docs/WALKIE.md"，不是光秃秃一个文件名）。

**怎么刷**：沿用 `/reply` 轮询（1.2s），把 `steps` 和 `now` 一起带回来，前端只 append 并自动滚到底。
不用 WebSocket —— 一行一行冒出来的观感，1.2 秒的节奏已经够了。

**答完之后整个故事折成一行**（`他做了什么（N 步）`），想复盘再点开。

### 6. 结果怎么看：页面给摘要，详情去文件

手机上塞不下工作结果，而且结果本来就是**文件**。

| | 显示什么 |
|---|---|
| **对讲机页** | 摘要（一两句 + 可播报），够判断"成了没有、要不要细看"；回复短（< 700 字）时整段摊开，因为折叠会挡住里面的文件引用 |
| **文件浏览器** | 详情。复用 Nexus 现成的 `WorkspaceBrowser`，**根目录就是当前这一格的 cwd** —— 换一格，看到的目录跟着换 |
| **过程里的文件名** | 可点，直接跳到那个文件 |

> 就是你说的那个比喻：**能听见他说话（摘要 / 播报），也能看见他电脑上的东西（文件）。**
> 两件事在同一个屏幕上，但分属两个层次 —— 说话是"结论"，文件是"证据"。

### 7. 回复里的文件引用可以直接点开

既然 Claude 的回复本来就带路径（`` `src/walkie/api.ts` ``、`[README](./README.md)`），
那让它直接可点就省掉了"记住路径 → 开浏览器 → 一层层翻"三步。

`frontend/src/walkie/replyLinks.tsx` 认三种写法，按可靠性排序：

| 写法 | 例子 | 处理 |
|---|---|---|
| markdown 链接 | `[README](docs/X.md)` | http(s) 走外链；其余当路径 |
| 反引号 | `` `src/walkie/api.ts` `` | 像路径就可点，否则按普通代码渲染 |
| 裸路径 | `docs/WALKIE.md` | 后缀在**白名单**里才认 |

**白名单是必须的**：没有它 `v4.9.1` 会被当成文件名。路径后面的 `:12-15` 行号会被剥掉 ——
文件浏览器还不能跳行，留着只会让路径打不开。

点下去不是只开浏览器，是**直接定位到那个文件所在的目录并打开它**。

### 8. 播报

自动播摘要（松手后听见一句结论，是对讲机的核心体验）。

**播报状态要记"在播哪一个"**，不能只用一个布尔：两个按钮共用一个布尔时，播摘要会让"全文"
也变成"停止"，想从摘要切到全文得先停一次。现在点另一个就是直接切过去。

### 9. 一轮对话在屏上长什么样

一屏只有**一个**主角，谁是主角看当下在干什么：

| 这一刻 | 屏上 |
|---|---|
| 待机（还没跟他说过话） | **什么都不画**。键会说话，就别再替它说一遍 |
| 正在说 / 正在改稿 | 上面一条"他上一轮"（暗一档、折三行），下面是你这一轮 |
| 他正在干活 | 你的话（一道竖线，**不是卡片**）+ 一行行往外跳的动作流 |
| 答完了 | 你的话 + 他的回复（主角）+ 过程折成一行「他做了 N 步」 |

三条规则：

- **你说的话不是卡片。** 它左边一道竖线、字色暗一档 —— 幻灯片式的卡片会把它抬到和他
  的回复同级，读的人得先判断该看哪张。
- **过程答完就折起来。** 「他做了 12 步」一行，想复盘再点开。摊着的时候它和回复一样重。
- **他上一轮的话留在录音/改稿期间。** 你在回他，不是在对空气说话；发出去那一刻它才让位。

（"再问一句"这个按钮**删了**：它做的事（清屏回到待机）按住讲话键本来就会做，
而且讲话键就在拇指底下。同一个动作给两个入口，只会让人犹豫。）

### 10. 草稿不丢

按频道各存一份，落盘到 `localStorage`（`nexus_walkie_state`，防抖 400ms），顺带记住
"上次停在哪一格"。打了一半被切走 / 锁屏 / WebView 被系统回收，回来时字和位置都还在。

### 11. 两条路：自己说 / 用输入法说

**先说结论：App 没有办法调用微信输入法的"按住说话"。** 不是难，是没有这条路 ——
输入法是另一个进程，它工具栏上那个麦克风按钮不对任何 App 开放；Android 也没有
"帮我按一下输入法某个键"的 API。（唯一能碰它的是无障碍服务去模拟点击，那要用户
专门去开无障碍、还随输入法改版就坏，不能拿来做主线。）

所以这一屏认两把麦克风：

| | 自己说（按住讲话键） | 用输入法说（点 ⌨） |
|---|---|---|
| 怎么用 | 按住，说完松手 | 点 ⌨ 起键盘 → 按**输入法自己的**麦克风 |
| 谁在转写 | 本机 SenseVoice（`~/work/intake`） | 输入法背后的服务（微信/讯飞/…） |
| 好在哪 | 一个手势、不用起键盘、**音频不出本机** | 识别质量通常更好（大模型 + 用户词库） |
| 差在哪 | 小模型 + 只喂了这段音频 | 要起键盘，多两步 |

**关键不是二选一，是两条路都拿到同样的后半程。** 无论字是从哪来的，只要落进那个
输入框，就走同一条：**自动精炼 → 可改可还原 → 发送 → 看过程 → 收回复**。
以前精炼只挂在自己的语音后面，用输入法说的字是"二等公民"；现在不是了。

怎么认出"这是输入法在说话"而不是打字：**一次塞进来一长串**（≥6 个字符算一次语音提交，
打字是一个字符一个字符来的）。判断错了也不致命 —— 「还原原文」就在旁边。

> 这一条本身也是个取舍：**当平台生态里已经有更好的东西，别做一个更差的去跟它比。**
> 我们能加的价值不在"再识别一遍"，而在它后面那一整条链路。

### 12. 明确不做

- **不做流式 WebSocket**：1.2 秒轮询够用，少一套状态要维护。
- **不在对讲机页里渲染完整 markdown 回复**：那是文件浏览器和老终端的活。
- **不做多频道同时收听**：一次只有"当前这一格"。
- **不把台面做成可缩放/可拖拽**：它是**手**用的，位置尺寸固定。
- **动作流只有"工具级"粒度**：看不到工具内部的输出。想看那个就点文件名或去经典终端。

## 三、变更记录

按时间倒序。每轮都是真机/模拟器用过之后提出来的，写清楚**根因**而不只是改了什么。

### v4.19.0 · 消息流重做：先扫一眼，再读

v4.18 用了一轮之后给回来的反馈：**"上一版那个对话流感觉还不错，这一版怪怪的"**。
问题全在消息流上 —— 排了 13 节的评审（见第十一节），
结论是：**这一屏的第一职责是"扫一眼"，而 v4.18 把它做成了"逐条读"。**

- **每条默认折成三行纯文本**（`PREVIEW_AT = 140`），**点整条正文**才展开成 Markdown。
  根因：v4.18 每条都全渲染 Markdown，一条长回复能占满一屏 —— 一屏一条，翻不动，"扫"没了。
  折起来时**路径仍然可点**（`Preview` 会挑出裸路径做成按钮），不然开个文件还得先展开。
- **删掉了「展开全文」那个 12px 小字按钮**：一个消息的入口做成小字，就是点不到。
  **整条正文都是命中区。**
- **署名挪到内容之前**，并且给全：`工作区路径 · channel 名`。
  根因：一段对话里"谁在说"是第一信息，比内容更先被读到，不该做成脚注。
- **我和你靠位置分开**（我右、它左）+ 底色。原来靠两道 2px 的竖线（琥珀/灰）承担"身份"，
  余光里分不出来 —— 反馈的原话是"我看不出来哪个是我说的，哪个是 AI 说的"。

  句子的另一半，而且长句会在 `maxSegmentS`（原 9 秒）处被**硬切**在词中间。现在整段是最终
  结果，分段只是预览；整段失败就退回分段的，绝不因此丢字。顺带把硬切上限放宽到 12 秒。
  （实测：干净语音上两者结果相同 —— 你自己的声纹样本两种方式都转对了。收益在长句和边界。）
- **回复改成只取最后一段话**（#49）。根因：一轮里有很多段 text，中间那些是**过程叙述**，

### v4.12.1 · 切走再切回来，过程不见了

- **根因**：`peekInto()` 拿 `text` 当门槛 —— 而**正在干活的那一轮 `text` 本来就是空的**

- **讲话键从圆心 90px 变成整块拇指区**，并且**有草稿时分裂成两个键**（按住重说 / 发送）。
  根因：上一版用一个圆的两种手势表达两件事，判定靠"按了多久、录到声音没有"去猜，
  还得在按下瞬间偷偷把草稿存起来（因为开始录音会清空输入框）。一个圆扛两件事，
  代价就是这一串补丁 —— 现在两件事各有各的键，不需要猜。
- **待机屏的两行提示删掉**（#38）。根因：它和讲话键上印的字一模一样，而讲话键就在
  40px 之外。**会解释自己，就说明设计没到位** —— 这里正确的修法不是换个说法，是删。
  删完的待机屏是一片安静的黑 + 一个占满拇指区的大键，读作"还没有人的话落在这"。
- **非 Claude 的格改成由讲话键自己承担**（#39）。根因：上一版"上面一行黄字说已拦住 +
  下面一个照常能按的讲话键"是**自相矛盾**的 —— 用户会对着一个明知会被拒的东西按下去，
  白说一遍再被拒。现在键本身换成警示样式，文案就是拦住的理由 + 下一步，点它跳走。
- **答完之后过程折成一行**（#40）。根因：两张同级的卡 = 让读者做一次无谓的取舍。
- **你说的话不再是卡片**（#41）。根因：卡片是"并列的几件事"的语法，而这里只有一件事
  是主角。一道竖线就够表达"这句是我说的"。
- **「再问一句」删掉**（#42）。根因：它和按住讲话键是同一个动作（都是清屏回待机），
  同一个人在同一个屏上给两个入口，只会让人犹豫一下。
- **屏改成从下往上长**（`justify-content: flex-end`）+ 录音/改稿期间保留"他上一轮"
  当上下文（#43）。根因：内容居中时，那块空读作"这里本来该有东西"；贴底之后它读作
  "还没收到"。而你在回他话的时候把他上一轮撤走，是在对空气说话。
- **修掉回复追踪里的两个偏移量**（#44）。这是**自查时踩出来的真 bug**，而且正好是本项目
  历史上最痛的那类故障。链路和根因：

  ```
  发送 → 记下目录里各 jsonl 的字节数（基线）
  认领 → 扫尾部 256KB，找内容对得上的那条人类发言
        ↳ 老代码：claim(..., sizeOf(f), 'text')  ← 拿了**文件当前大小**
  增量读 → readFrom(file, 文件大小 - 4096)
  ```

  两条都错在同一个地方 —— **偏移量算错了**：
  1. 认领命中时应该用**那句话自己的字节偏移**当起点，老代码用的是"文件此刻的大小"。
     一句"收到"之后可能跟着几万字节的记录（推理块、工具调用），于是增量读从
     `大小 - 4096` 起步，**永远读不到我们自己发的那句**，`sawSent` 一直 false，
     60 秒后报「这条消息没有出现在会话记录里」—— 而此时 AI 早已答完，就摆在文件里。
     （实测：那句话在 335,112 字节处，起点却算成了 381,876。）
  2. 尾部扫描里，砍掉半个行头之后的偏移量拿 **JS 字符串下标** 在加 —— 中文一个字 3 字节、
     下标只加 1，偏移越错越远。还有一处 `slice` 出来的新起点也混了字符串下标和字节数。

  修法：`readTailAt()` 把正文起点按 `Buffer.byteLength` 算准并带回来；认领命中时用命中
  那行自己的偏移当基线，且**当场就把 `sawSent` 立起来**（"认领成功"和"确认送达"本来就是
  同一件事，分成两步做只会在两步之间的缝里丢掉整轮回复）。
  验法：连发四条不同的话，`reply` 的 `via` 都是 `text`、`text` 就是那句话的回复。

  > 教训：**凡是把"位置"当判据的地方，位置必须在同一个坐标系里算。**
  > 这次是"字节 vs 字符"和"命中点 vs 文件末尾"两种坐标系混用，两种都静默。

## 五、它是怎么工作的

```
┌── APK（风味包 walkie）───────────────────────────────┐
│  WalkieApp.tsx                                       │
│    ├─ Tuner.tsx         两排调台条：上排工作区 / 下排 Agent  │
│    ├─ speech.ts         按住说话 → 转写（三条路，见下）    │
│    ├─ api.ts            → /api/walkie/*              │
│    └─ tts.ts            回复 → 语音播报                │
└──────────────────────────────────────────────────────┘
                        │ HTTP（同一份 bundle，浏览器里也跑得起来）
┌── Nexus 后端 walkie.js ──────────────────────────────┐
│  GET  /api/walkie/channels     频道清单（含"是不是 claude"）│
│  POST /api/walkie/send         paste + Enter 落到输入框   │
│  POST /api/walkie/refine       口语 → 精确指令（LLM）     │
│  POST /api/walkie/summarize    回复 → 一句口播摘要（LLM）  │
│  GET  /api/walkie/reply        这一轮的回复 + 动作流 + 回看 │
└──────────────────────────────────────────────────────┘
                        │ tmux
              project(session) : channel(window)
```

### 1. 选频道 —— 两排横向条，不是列表、也不是旋钮

上排是 project（tmux session），下排是 channel（tmux window）。左右拖，**项跟着手指走**，
停稳吸附到最近一格并震一下；直接点某一格就是跳过去。

**滚动不自己实现**，用浏览器原生的 `scroll-snap` —— 惯性、橡皮筋、跟手都是系统的。
"现在停在第几格"按 **"哪一项的中心最贴近容器中心"** 算（`Tuner.tsx` 的 `position()`），
项宽不等也成立；然后按跨过几个细分配轻响、跨过几个整格配重响 + 震动。

**两排各自有颜色**（琥珀 = 工作区、蓝 = Agent），选中态、小灯、色块共用同一套色。
CSS 变量按**语义**命名（`--tone-ws` / `--tone-agent`）—— 位置是会换的，按位置命名改一次全乱。

**只在停稳时提交一次。** 拖动途中读数自己跟跳，但换台要打断语音、清空草稿、去拉上一轮
回复，每过一格调一次既不必要也很贵。

**手感**：每过一个细分合成一声轻"嗒"（只有声音）；过整格是重"咔"（噪声瞬态 + 一层 430Hz
的 body + 三个不同衰减的谐振，每声有微扰，不是循环同一个采样）+ 一次 `impact(Medium)`；
停稳一声低沉的"咚" + `impact(Heavy)`。

> 震动**不能**用 `navigator.vibrate`：它在 Android WebView 里存在、调用还返回 `true`，
> 但 Chromium 的 WebView 没实现 VibrationManager，是静默空转。必须走 Capacitor 的
> Haptics，那才是真的在驱动马达。
>
> 也不能用 `selectionChanged()`：插件源码里是 `if (this.selectionStarted)`，不先调
> `selectionStart()` 就完全不震 —— 这就是 v4.11 之前"每过一格震一下"一次都没震过的原因。

### 2. 说话 → 文字（按住说话的实时转写）

**不是 Android 的 `SpeechRecognizer`。** 真机实测过：权限给了、按下去也进了"松手结束"
状态，但**一个字都不吐** —— 国产 ROM 上没有可用的 Google 语音服务，而那个插件出错是
静默的（`partialResults` 模式下 `onError` 的 `reject()` 打在了一个已 resolve 的 call 上，
JS 侧什么都收不到，`listeningState` 也不发）。按住说话于是变成按住没反应，且没有任何提示。

现在走的是：

```
按住 → getUserMedia（带 AEC/降噪）→ AudioContext → ScriptProcessor → Float32 样本
     → 按静音切段（最简 VAD）→ 每段编成 WAV 单独 POST
     → Nexus 转给本机 intake（:59011）→ sherpa-onnx SenseVoice-small-int8 转写
     → 文本按段落顺序拼起来，边说边冒出来
松手 → 拿**整段**音频再转一遍 → 那才是最终文字（分段那几遍只是预览）
```

**为什么能"边说边出字"**：本机 ASR 的模型常驻之后，解一小段只要几十毫秒
（实测 3–5 秒的音频 ~0.08s；早先记的"1.4 秒固定开销"是**冷启动**时测的，
模型加载完就不成立了）。所以切成小段分别转几乎不额外花钱。切段只发生在**能量低谷**
（静音持续 420ms 之后），段尾天然落在自然停顿上，不会把词切坏。

**但分段只是预览。** 松手时会拿整段录音**再解码一次**，那才是最终发出去的文字：
一次解码看得见整句话的上下文，也不会在 `maxSegmentS` 那一刻被硬切在词中间。
整段这一遍失败就退回分段拼出来的 —— 绝不因为"想更准"而丢字。

**两道防幻觉的门**（都踩过）：
- 阈值自适应。底噪高的设备上固定阈值会永远不"静音"，只能靠上限硬切；
- 一段里"有声"的部分不足 0.25 秒就整段丢掉。只按长度过滤的话，**纯噪声会被送去转写，
  而 SenseVoice 会一本正经地为它编出一句话**（模拟器上静音输入转出过 6 个字的幻觉）。

**为什么不用 MediaRecorder**：它只能整段拿走音频，中间插不进去，想要边说边出字就必须
能按段切。顺带也省掉了 MediaRecorder 那套容器格式协商（不同 WebView 支持的 MIME 不一样，
是个静默的坑）。代价是 `ScriptProcessorNode` 是废弃 API 且跑在主线程 —— 但它到处都有，
而 AudioWorklet 要单独加载模块文件，在 WebView 里多一层不确定性。

> 音频不出本机：转写跑在 `~/work/intake`，与会议录音共用同一套 ASR，只有一份实现。
> 首次按下会弹系统的麦克风权限框，界面会先显示「正在打开麦克风…」（权限框期间
> getUserMedia 还没 resolve，不提示的话就是一个看起来按了没反应的死按钮）。


### 3. 口语 → 精确指令（松手即自动精炼）

纯口述必然带大量口水话。**只要字落进输入框就自动精炼** —— 不管是按住说话转出来的，
还是用输入法的语音键说出来的（见第二节第 11 条）。

> 「呃那个我想让你帮我看一下，就是说我们那个项目里面那个 README 嗯好像有点旧了，
>  就是很多那个安装步骤都不对，你帮我把它更新一下，然后呢顺便把配置那一节也补充完整一点」
>
> ↓
>
> 「更新项目 README：修正安装步骤，补充完整配置章节。」

精炼**只是替换文本框里的内容**，不是拦截：你随时能改、能「还原原文」；按发送时发的是框里
此刻的文字。精炼失败或超时（3 秒）也绝不挡发送 —— 宁可发原文。

用的是 `data/configs/<WALKIE_LLM_PROFILE>.json` 里已有的 profile（默认 `deepseek`），
不新增任何密钥。profile 缺失时 `/refine` 原样返回输入，功能自动降级。

### 4. 投递：直接落到那个频道的输入框

`POST /api/walkie/send` 走 tmux，不经过 PTY：

```
tmux load-buffer -b nexus-walkie -     ← 文本走 stdin，绕开 shell 引用和参数长度限制
tmux paste-buffer -b nexus-walkie -t <session:window> -d -p
   ↳ -p 是 bracketed paste：多行文本会原样进入输入框，而不是被拆成多次回车提交
（等 260ms，TUI 要先消化完粘贴内容，否则回车会被当成换行）
tmux send-keys -t <session:window> Enter
```

**护栏**：目标 pane 里没有 claude 就拒发（409）。`/channels` 会用一次 `ps` 做进程树 BFS
给每个频道打上 `kind: 'claude' | 'other'` 标记，前端据此禁用发送、调台条上标 ⚠。前端拦一道、
后端再拦一道 —— 防的是绕过前端直接打 API。否则「更新一下 README」会被 zsh 当命令执行。

### 5. 回复：从 Claude Code 的 transcript 里精确取

最不显然的一块。同目录下可能并行跑着好几个 claude（vault 就有 5 个），所以「哪个
transcript 是本频道的」**不能靠 mtime 猜**。判据用内容：

1. 发送前记下 `<slug(cwd)>/` 下所有 `.jsonl` 的大小
2. 发送后轮询，找**变大且里面新出现的 human 发言文本和我们刚发的对得上**的那个文件
3. 认定后只增量读新增字节，靠 `type=system, subtype=turn_duration` 判回合结束
   —— 这是 Claude Code 自己写的「本轮答完了」标记，比在 TUI 上猜 spinner 稳得多
4. 认下来的 sessionId 落盘 `data/walkie-sessions.json`，**重启后仍能回看上一次的回复**

追踪是**按频道各自独立**的（`Map<频道, timer>`），不跟着视野走：切到别的频道看看、
甚至在那儿再问一句，原来那轮答完了照样落进缓存，切回去就还在。

## 六、回复为什么不会再"卡住"

第一版真机上栽过一次：**内容发出去了、界面显示"AI 在干活"，然后永远没有结果**。

根因是追踪器是内存态 —— 进程重启或超过 `KEEP_DONE_MS` 被回收之后，`/reply` 返回一个空的
`{state:'idle'}`，前端就一直转到自己 10 分钟超时。

现在三道防线：

1. **没有活跃追踪时一律回看该频道上一次的回复**（读 `data/walkie-sessions.json` 记下的
   transcript 文件），而不是只在 `peek=1` 时回看；
2. **认领会话靠位置，不靠文本**：发送前记下 transcript 文件的大小，之后**追加的第一条
   人类发言**就是我们发的那句。文本对得上只是更强的确认，不是必要条件 —— 早先版本要求
   文本前缀匹配，真机上被多敲进一个字符就失效，于是永远等不到结果。60 秒还认不出就明确
   报「这条消息没有出现在会话记录里」，不让界面干转到超时；
3. **把过程摊开**：等待时把动作流和窗口现状都显示出来，认领失败时给出具体原因
   （比如"这个频道的目录还没被 Claude 信任，它在等确认"）。

**v4.12.0 又补了一条 —— 防线本身也会算错。** 上面第 2 条说"认领靠位置"，但那个位置是
**字节偏移**，而它有两处坐标系错误（用"文件当前大小"而不用"命中那行自己的偏移"、
拿 JS 字符串下标当字节数），结果是：认领明明命中了，增量读却从错的地方起步，永远读不到
我们自己发的那句 → 60 秒后报「这条消息没有出现在会话记录里」——**而此时 AI 早就答完了**。

这是比"卡住"更坏的一种失败：**它不是没反馈，是给了错的反馈**。用户看到那句话会去重发，
然后更困惑。根因和修法见第三节 v4.12.0。

## 七、两个 APK

不是为了省事才做成两个包，是因为**这是实验**：不想动每天在用的那个。但也**不该**维护第二份
Android 工程（gradle 壳子、图标、签名、Capacitor 配置都得跟着同步，迟早不一致）。所以用
Gradle product flavor，同一份代码、同一份 web 产物：

| | classic | walkie |
|---|---|---|
| applicationId | `com.librae.nexus` | `com.librae.nexus.walkie` |
| 应用名 | Nexus | Nexus 对讲机 |
| 图标底色 | 白 | 深色 `#0F172A` |
| `assets/public/ui-mode.json` | `{"default":"classic"}` | `{"default":"walkie"}` |

两个 applicationId 不同 ⇒ 可以同时装在手机上，数据互不干扰（localStorage 按包隔离，
FileProvider authority 也跟着 applicationId 派生，不会撞）。

前端启动时按 **URL 参数 → localStorage → `ui-mode.json` → classic** 的顺序定模式
（`frontend/src/walkie/mode.ts`）。浏览器里那个 probe 会命中 SPA 兜底拿到 index.html，
content-type 不是 json 就当没有这个文件 —— 所以浏览器行为与改造前逐字节一致，不需要构建
两份 bundle。

```bash
cd frontend && npm run build          # 先出 web 产物
./android/build-apk.sh assembleWalkieRelease    # 只出对讲机包
./android/build-apk.sh assembleClassicRelease   # 只出经典包
./android/build-apk.sh assembleRelease          # 两个都出
```

产物：`android/app/build/outputs/apk/<flavor>/release/app-<flavor>-release.apk`

在经典界面里，只有出厂默认是对讲机的那个包会多一个右下角的「🎙 对讲机」浮标用于切回；
浏览器用户从没见过对讲机，不会凭空多出按钮。

## 九、已知边界

- **调不了输入法的按住说话**：输入法是独立进程，它的工具栏按钮不对 App 开放，
  Android 也没有这类 API。所以"用微信输入法的麦克风"这条路的入口是**键盘**，
  不是这一屏的键（见第二节第 11 条）。能碰它的只有无障碍模拟点击，代价和脆弱度都不值。
- **"整句提交"会被当成语音输入**：输入框里一次进来 ≥6 个字符就触发精炼。正常打字不会
  这样，但**粘贴**会 —— 粘一段命令进来也会被精炼一遍。判错不致命，「还原原文」在。
- **震动不能走 `navigator.vibrate`**：它在 Android WebView 里**存在**、调用还返回 `true`，
  但 WebView 没实现 VibrationManager，是**静默空转**。必须用 Capacitor 的 Haptics。
  同一个坑还有两处：`window.speechSynthesis` 在 WebView 里根本不存在（TTS 只能靠插件）；
  Haptics 的 `selectionChanged()` **必须先 `selectionStart()`** 才会震（插件源码里是
  `if (this.selectionStarted)`）—— 所以早先那版"每过一格震一下"其实一次都没震过，
  手上只有吸附那一下。**接震动/音频/传感器之前，先读插件的原生实现，别信 JS 侧的返回值。**
- **细分刻意不震**：一秒钟能划过十几个细分，每个都震会让马达变成背景噪音、手指发麻，
  反而把"到节点了"这个信息淹掉。震动只留给节点，节点才显得重。
- **一次只认真追一轮**：同一频道重复发送会顶掉上一轮的追踪（新的一轮更重要）。
- **转写依赖本机 intake 服务**：`intake` 没在跑时按住说话会明确报「本机转写服务没在跑」，
  此时可点 ⌨ 用输入法语音键顶着。
- **回复的粒度是「这一轮的文字输出」**：只调工具不说话的那一轮会显示「（这一轮没有说话，
  可能只动了文件）」。想看完整过程还是回经典界面。
- **`turn_duration` 拿不到时**（老版本 Claude Code / 被中断）退化成「认领成功 + 有正文 +
  文件静默 6 秒」判定，界面上会标「（靠静默判定结束）」。

## 十、产品重审（2026-10-03）：它不该是对讲机

> 这一节不是"再加点什么"，是**把之前的思想包袱清空，重新问一遍这是什么产品**。

### 0. 起点：你问的那个问题

> "我真的是要一个 Walkie 吗？我只是要一个极致简洁便利的和 AI 交互的方式。

这句话把产品的定义换掉了：**从"遥控一个 agent"换成"接住我的真实世界"**。

### 1. 冷启动实况（未看文档、以用户身份直接开屏）

打开是**一片黑**（上半 55% 什么都没有）。顶栏 5 个按钮：`🔊 ↻ 📁 ⌨ 经典`。

### 2. 证据（数出来的，不是印象）

| 发现 | 证据 |

| **第一控制轴是 shell 窗口名** | 现存频道：`deepseek-1` `deepseek` `apk stevejobs` `walkie-re` `对讲机测试` `shell` `people` `工作流自动化`。没有哪个产品会以"我的第几个 shell 窗口"作为主控 —— 这是终端漏出来的 |

### 3. 主要结论：**"对讲机"这个比喻的前提是错的**

对讲机是半双工的 —— **说话之前你必须先选人、选频道**。这个约束来自无线电频谱，不来自你。
而你说出来的那些话（地铁上的一个判断、饭桌上听到的一个名字、脑子里半成形的想法）
**恰恰大多还不知道该给谁**。

**那正是它该替你做的决定。** 现在做成了一个"选人"的机器，而你要的是"接住"。

### 5. 提案：它应该是什么

**一句话**：**一个键，说一句，它接住、办掉、用话回你。**

```
┌──────────────────────────────┐
│  一条流（从下往上长）           │  你说的 / 它办的 / 它回给你的
│  每条只带一个"寄到哪"的小标签   │  ← 它猜的，可改，不用你先选
│                              │
│  ┌────────────────────────┐  │
│  │        按住说           │  │  ← 唯一的一个键
│  └────────────────────────┘  │
└──────────────────────────────┘
```

- 没有工作区、没有频道、没有模式、没有第二个 App、没有逃生口。
- **松手以后你的事就结束了**：要不要发、发给谁，是它的事。
- **回话走声音**：走路时你听得见结论。

**顺手能砍的（Cut list）**

| 砍掉 | 为什么 |
|---|---|
| **两排调台条**（含 `Tuner.tsx`、调台音效与震动） | 它在让你回答"哪个目录 / 哪个 shell 窗口"。路由改成系统猜 + 事后一个可改的小标签 |
| **「经典」按钮 + 第二个 APK 风味包** | 一个产品。深活去桌面浏览器做，这一屏不做终端 |
| **顶栏 5 个按钮 → 1 个以内** | `🔊 ↻ 📁 ⌨ 经典` 比台面还热闹 |
| **过程流占主屏** | `第 1 步：… ▸ Sleep 15 seconds` 折成一行口播（"他在改 README"），要复盘再点开 |
| **"不是 Claude"的告警态** | 自动路由之后根本不会把你送到 shell；这条状态是为手工选人而存在的 |
| **"已精炼 / 还原原文 / 清空" 当一张待批卡** | 精炼是它替你猜的，不该要你批（见下 fix 3） |

**按序要做的（Fix list）**

1. **删掉"说话前的一切决定"。** 台面只留一个键；目标由后端按"你最近在哪个目录干活 /
   这句话像谁的事 / 谁空着"自动选，松手后显示成一个可改的小标签（`→ ~/work/nexus · deepseek ▾`）。
   **默认必须对，错了一次点改** —— 像输入法的自动更正，不是像表单。
2. **回话走声音，不走屏。** 结论用一句口播（LLM 摘要 + TTS 已经有了），过程只留一行"他在干什么"。
   判据：**把手机塞回兜里，你能知道这事办完没有、办成什么样。** 今天做不到 —— 你得掏出来读。
3. **松手即完成。** 精炼稿不该是一张要你按"发送"的卡。它落成一条记录并且**已经开始跑**；
   要拦，点"等等"。发送是第二个决定，而这一屏全部的价值就在于它只有一个决定。
4. **冷启动必须是产品，不是残渣。** 现在回访者第一眼是上一轮的"他的回复（这一轮没有说话）"。
   改成一条干净的空流 + 那个键。
5. **世界的入口不能只有嘴。** 你的原话是"我是它在真实世界的 context 入口"，而你的真实世界
   大量是**图**：一页 BP、一张名片、白板、幻灯片、合同。现在只有音频。
   （**这条要你拍板，不是我要加的**：如果要，就按"相机进来 → 调台条出去"换。）

**三条判据**（以后拿它做取舍）

1. 说话之前要做的决定数 = **0**。
2. 屏上要么是你说的一句，要么是它回的一句 —— **没有第三样东西**。
3. 世界的入口不能只有嘴。

|---|---|---|
| **"扫一眼"变成了"逐条读"** | 每条都全渲染 Markdown，一条长回复占满一屏。**内容越完整，信息越少** —— 这一屏的主屏失去了唯一的职责 | 默认折成三行纯文本，点开才是 Markdown |
| **"谁在说"被做成了脚注** | 11px 灰字挂在内容**下面**，而且还只有名字。一段对话里说话人是**第一信息**，比内容更先被读到 | 署名挪到内容之前，给全`工作区 · channel` |
| **错误/边界配不上主角**（身份） | 两道 2px 竖线（琥珀/灰）承担"我 vs 它" —— 余光里分不出来 | 用**位置**（右/左）+ 底色分开 |
| **入口做成了小字** | 「展开全文」是一个 12px 按钮。「一个消息的入口做成小字，就是点不到」 | 整条正文都是命中区 |

**判据（以后拿它做取舍）**
1. 一屏**至少**要能放下 4-5 条消息（现在折叠后是 4-6 条）。
2. 每条消息的**第一行必须是"谁"**。
3. 一个消息最多两个手势，而且各自有**够大的靶子**（不小于 32px）。
4. 折起来的东西也要能用 —— 路径不因为折叠而失去可点性。

### 版面：三个带

```
┌────────────────────────────────────┐
│ ● 我的机器 · 3 个在跑        🔊 经典 │  顶栏：这台机器现在的样子
├────────────────────────────────────┤

├────────────────────────────────────┤

│ → ~/work/nexus · deepseek ▾        │  寄给谁（记住的，不是选的）

```

**新的在最上面。** 它不是聊天记录，是一块状态牌 —— "现在怎么样"永远在第一眼的位置，
不用往下翻。所以这一屏**没有"自动滚到底"那套逻辑**，也就没有"你往上翻会被拽回去"。

### 主屏：**跨所有会话**的一条流

它是这一屏的全部差异，也是"它不是 chat app"的唯一依据。数据来自每个 claude 频道的
transcript（和追踪回复用的是同一份事实来源），每个回合取**人类那句 + 它最后说的一段**。

| 屏上 | 从哪来 |
|---|---|
| `● 正在跑` | 那一轮没有 `turn_duration`，**且**文件里最新一条记录在十分钟内 |
| `▸ 它说的` | assistant 的**最后一段** text（中间那些是过程叙述，进不了流） |
| `▸ 你说的` | human 记录里 `isMeta` 不是 true 的那些（斜杠命令的输出不是你"说"的话） |
| 路径 | 那个频道 pane 的 cwd，家目录缩成 `~` |

**看不见的判据**：截图里同时出现 5 个不同目录的活（`~`、`~/work/server-admin/…`、
`/mnt/nas/notes/vault`、`~/work/wechat-agent`、`~/work/nexus`），其中大多数**不是**从手机发出去的。

### 输入框：一个框、一个附件、一个发送

- **语音不自研。** 转写交给输入法（它更好，而且按住说话那个按钮本来就是别人键盘上的）。
  判据还在：**一次塞进来 ≥6 个字符 = 输入法整句提交**，自动精炼；点字是一个一个来的，
  不会误伤。**粘贴不算** —— 粘进来的东西本来就该原样发出去，靠 `paste` 事件区分。
- **附件 = 把眼前的东西交出去。** 传上去落在 `~/nexus-inbox/<日期>/`，**绝对路径写进那句话里**
  （Claude 读一个路径就够了，不需要发明上传协议）。不往你的仓库里丢文件。
- **寄给谁是一行小字，不是一道题。** 记住上次；点开才有列表，按**目录**分组 ——
  目录才是人认的地方，窗口名只是"这个目录里的哪一个人"。

### 它怎么工作

┌── APK（风味包 walkie）──────────────────────────┐

### 已知边界

- **一个回合大到把 256KB 尾巴占满时**，那个频道切不出回合 —— 兜底是把它最后说的那句放进流，
  但"你说的那句"就看不见了。
- **十分钟门槛**：跑一个十分钟以上的长命令会被判成"不在跑"（那种情况该去经典界面看）。
- **流只画最近 14 条**（正在跑的另算）。它是"现在怎么样"，不是档案。
- **一次只追一轮**：同一频道重复发送会顶掉上一轮。
- 附件落在 `~/nexus-inbox/`，**会一直堆着** —— 还没做清理。
- **"自己写一个答案"走的是"跳过 + 一句话"**，不是把文字填进面板里那一项（实测 `Type something.`
  和 Esc 等价，都是跳过）。所以在它眼里这道题是"用户没选"，答案是你随后那句话 —— 结论对得上，
  但如果你想让某个选项被正式记进那次工具调用里，得用图上给的选项。
- **一次问多道题时，前端要求每道题都有答案**才让送。差一道就送，终端会停在半道上（后端会拒并报错）。

### 8. 追问（同日）：那它跟一个 AI chat app 有什么不同？

> 用户当场追问：**"做到最极致只留一个输入框、语音直接用输入法、最多加个附件按钮 ——
> 那它跟 WorkBuddy 这类手机端 AI App 有什么不同？"**

**先承认：没有不同，而且更差。** 腾讯 WorkBuddy（2026-07 三端上线）已经做了"连接电脑、
远程操控桌面端"，多模态输入、任务列表、完成通知、跨端同步、技能市场，全都有人维护。
**如果这一屏的答案是"一个输入框"，那就别做 —— 直接用它的。**

**但它有一件结构上做不到的：它的另一端是它自己的 agent，不是你的计算机。**

| | WorkBuddy 这类 | 这一屏该做的 |
|---|---|---|
| 另一端 | 厂商的 agent（云端沙箱，或它自己的桌面端） | **你的 shell、你的文件、你已经在跑的那些 claude** |
| 能干的事 | 它的技能库允许的事 | shell 能干的任何事（vault、intake、CDP、重启服务） |
| 上下文 | 你喂给它的资料 | **它本来就住在那儿的那些文件** |
| 主屏 | "我交给它的任务" | **"我的机器在干什么"** |

**判据一条就够**：**能不能看见"你没通过手机下的那些活"。** 你白天在终端里开的那 20 个窗口，
手机上应该看得见、能插手。chat app 结构上永远看不到这一屏 —— 因为它的另一端只有它自己。

**推论（这才是"极致简洁"该简的地方）**：简的是**你这一侧**（一个键 / 一个框，用输入法都对），
